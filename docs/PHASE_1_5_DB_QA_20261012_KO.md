# WhatEatO — Phase 1.5 DB 안정화 QA (2026-10-12)

## 범위 / 변경 원칙
- 기존 DESIGN LOCK v1.0 유지. 잠긴 UI/CSS 파일 변경 없음.
- 기존 `restaurants` 및 리뷰/영업시간 테이블을 수정하거나 삭제하지 않음.
- `004_i18n_analytics.sql`은 추가 테이블·인덱스·태그 사전만 생성하는 비파괴 마이그레이션.
- 외부 평점을 임의로 복제하거나, 출처 미확인 태그·메뉴·사진·설명을 발행하지 않음.

## 안전한 작업 순서와 실제 결과
1. Neon 운영 브랜치 `production`의 `restaurants` 행 수와 UUID 중복 여부 확인: **10,000건 / 고유 ID 10,000건**. 현재 샘플 데이터 10,000건은 **서울특별시**에만 해당.
2. 별도 Neon 스테이징 브랜치 `staging-phase1-5-20261012` 생성. 운영 원본을 복제한 뒤 **19개 SQL 문장을 단일 트랜잭션**으로 실행하여 migration 004 적용. 동일 문장 재실행(idempotency) 성공.
3. 배포 전 시점의 별도 복구용 Neon 데이터 브랜치 `backup-pre-phase15-20261012` 생성 완료. **Neon 브랜치 사본이며 별도 다운로드 백업/snapshot은 아님.** 컴퓨트가 없는 브랜치로 보관. 현재 플랜의 protected branch 상한 때문에 보호 설정은 실패했으므로 삭제하지 말 것.
4. 스테이징에서 API가 사용하는 식당 검색 SQL을 `en/ko/ja` 및 지역·태그·페이지 경계값으로 검증. 승인된 태그가 0건일 때 검증되지 않은 검색 결과를 태그 결과로 위장하지 않음. 식당 상세 조회 SQL도 대표 샘플에서 결과 확인.
5. GitHub PR #6에서 `has_more` 페이지 경계 버그 수정: `LIMIT limit+1` 조회 후 실제 반환 개수는 `limit`으로 자르고 나머지 행 존재 여부로 판정.
6. **CI / Design Lock 검증 통과**, 운영 전 검증용 스크립트 `scripts/verify_phase15_staging.mjs` 추가. 실행 시 선언된 Neon staging branch ID와 DB 내부 `neon.branch_id`가 일치해야 하므로 운영 DB 오접속을 차단하는 검사 포함. 해당 스크립트는 CI에서 구문만 검사하며 실제 원격 실행에는 별도 staging 접속 문자열이 필요함.
7. 운영 DB에도 migration 004를 **19개 비파괴 문장으로 단일 트랜잭션 적용 완료**. 작업 전 생성한 별도 복구 브랜치 유지. 운영 원본 데이터 변경 없음.

## QA 제한 및 배포 차단 조건
- **DB migration 완료 ≠ 웹사이트 배포 완료.** PR #6은 여전히 Draft이며 `main` 병합 / Hostinger·Next.js 실배포는 하지 않음.
- 스테이징에서 SQL을 직접 실행해 정상 동작을 확인했지만, 실제 웹 서버를 띄워 HTTP API 호출 / 브라우저 E2E 테스트를 수행한 것은 아님.
- 데이터가 10,000건뿐이므로 전국 규모/대량 트래픽의 검색 성능 보장은 불가. 대표 SQL의 워밍 상태 DB 실행은 수십 ms 수준이었으나 실제 왕복·콜드스타트·복잡 검색 지연은 별도 검증 필요.
- `/api/v1/analytics/events`는 반드시 프록시/WAF 기반 요청량 제한, 스팸 방지 정책, 운영 비밀키 세팅 및 30일 보관 삭제 작업 검증 후 공개할 것.
- 홈페이지 검색과 상세 화면은 아직 기존 UI/API를 사용하므로 새 `/api/v1/` 필드가 사용자 화면에 자동 반영된 상태가 아님.
- 브랜드 디자인은 OWNER APPROVED DESIGN LOCK v1.0을 유지하고, 검색 카드/식당 상세의 외관 변경은 별도 승인 필요.

3. 승인된 검색 결과 카드·상세 페이지 구조에 새 필드를 연결하되 **디자인 잠금은 그대로 보존**. 메뉴·사진·태그·별점은 출처/검증 데이터가 있을 때만 표시.
4. 샘플 식당의 출처·권한을 검증한 뒤 작은 규모로 데이터 보강 시작.
